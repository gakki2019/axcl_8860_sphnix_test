# RT 驱动调试

RT 驱动提供 `info` 和 `ipc_info` 两个只读节点，分别用于查看用户及管道信息、IPC 导出记录。可用于排查应用初始化、worker 关联和共享内存导入问题。以下命令在运行 AXCL 应用的主控端执行。

`rt/info` 的权限为 `0444`，普通用户可读；`rt/ipc_info` 的权限为 `0400`，通常需要 root 权限，因为输出包含共享标识和设备地址。若节点不存在，请检查 RT 驱动是否已加载，以及驱动版本是否包含该接口。

<a id="rt-user-info"></a>
## 1. 用户与管道：`rt/info`

```bash
cat /proc/ax_proc/rt/info
```

输出示例如下，数值仅供参考：

```text
========= Runtime Users Info =========
User[1]:
  pid:        1234
  refcount:   1
  report_num: 0
  Devices:
    Dev[1]:
      devid:   0
      Pipes:
        Group[1]:
          pid[0]:     1234
          pid[1]:     2345
          port_num:   2
          ports[0]:   100
          ports[1]:   101

```

| 字段 | 含义 |
| --- | --- |
| `User[n]` | 用户记录在本次输出中的序号，从 1 开始。 |
| `pid` | 该用户记录对应的主控端进程标识。 |
| `refcount` | 用户对象的内核引用计数。多个引用可以正常存在，需结合对象生命周期判断是否异常。 |
| `report_num` | 等待用户态读取的报告数量，包括设备事件、worker 退出等报告。 |
| `Dev[n]` / `devid` | 用户关联的设备记录序号及驱动设备标识。 |
| `Group[n]` | 当前设备下管道组的输出序号。 |
| `pid[0]` / `pid[1]` | 管道组登记的两端进程标识。Runtime 管道组通常对应主控端进程和设备端 worker；不关联 worker 的管道组中 `pid[1]` 可以为 0。 |
| `port_num` / `ports[n]` | 管道组的端口数量和各端口号，可用于关联 COMM 管道信息。 |

没有用户记录时，仅输出标题。设备和管道信息仅在存在对应记录时显示。

排查时按以下顺序查看：

1. 找到目标应用对应的 `pid`，确认驱动中是否已有用户记录。
2. 查看对应的 `devid`、管道组和端口号，再到 [COMM 调试](comm.md) 中检查管道状态及收发计数。
3. 如果 `report_num` 持续增加，检查应用是否及时读取事件和报告。该计数表示报告队列长度，需结合报告内容和日志判断是否异常。
4. 应用退出后仍有对应记录时，核对进程是否已退出、驱动句柄是否全部关闭，以及相关对象是否仍被引用。

<a id="rt-ipc-info"></a>
## 2. IPC 共享记录：`rt/ipc_info`

```bash
sudo cat /proc/ax_proc/rt/ipc_info
```

此节点列出全局 IPC 导出记录，用于检查共享标识、所有者、设备、内存属性和 PID 授权。统计范围仅包括 IPC 导出节点，不包括全部设备内存分配或消费者的本地引用。

### 2.1 输出示例

以下示例包含一条使用 PID 白名单的导出记录。`key`、PID 和地址均为示例值。

```text
========= AXCL RT IPC Info =========
[global]
node_count=1
node_limit=4096
snapshot_truncated=0
target_limit=64

Export[0]
key=000004d200000000000000010000000000000000000000000000000000000000
owner_tgid=1234
phys_devid=0
dev_pa=0x10000000
size=0x1000
mem_flags=normal
policy=whitelist
target_num=1
target[0]=5678

```

### 2.2 字段说明

| 字段 | 含义 |
| --- | --- |
| `node_count` | 本次快照包含的 IPC 导出节点数量。 |
| `node_limit` | 全局导出节点上限，当前为 4096。 |
| `snapshot_truncated` | `1` 表示快照容量不足，部分节点未包含在本次输出中；`0` 表示未发生容量截断。 |
| `target_limit` | 每个节点的 PID 白名单项数上限，当前为 64。 |
| `Export[n]` | 记录在本次快照中的序号，从 0 开始。跨次查询请使用 `key` 关联记录。 |
| `key` | IPC 共享标识，与应用导出、导入时使用的 `key` 对应。 |
| `owner_tgid` | 创建该导出记录的所有者进程 TGID，即进程级标识。 |
| `phys_devid` | 该记录所属的物理设备号。 |
| `dev_pa` / `size` | 导出记录中的设备地址和内存大小，均以十六进制显示，大小单位为字节。此处仅显示地址值。 |
| `mem_flags` | 内存属性，`normal` 或 `cached`。 |
| `policy` | `whitelist` 表示检查 PID 白名单；`disable_pid_validation` 表示禁用 PID 白名单校验，其他导入检查仍然适用。 |
| `target_num` / `target[n]` | 有效白名单项数及目标进程 TGID。白名单允许重复 PID，因此项数可能大于不同目标进程的数量。 |

当没有导出记录时，只有标题和 `[global]` 段落，`node_count=0`，没有 `Export[n]` 段落。

### 2.3 排查示例

**共享内存导入失败：**

1. 按应用使用的完整 `key` 查找记录。未找到时，检查 key 是否正确、导出是否成功、记录是否已释放；若快照截断，请重新采集。
2. 核对 `owner_tgid`、`phys_devid`、`dev_pa`、`size` 和 `mem_flags` 是否与导出端预期一致。
3. 如果 `policy=whitelist`，确认白名单包含导入进程的 TGID。授权按进程标识检查，并包含 PID 复用保护；新进程即使复用了相同 PID，也不会自动继承原进程的授权。
4. 结合导入接口返回码、设备在线状态和内核日志继续排查。记录和授权检查通过后，仍需满足其他导入条件。

**怀疑导出记录没有释放：**

在业务执行前后采集输出，按 `key` 和 `owner_tgid` 对比。确认导出端已释放对应记录，或最后一个相关驱动句柄已关闭。存在其他 IPC 应用时，`node_count` 可以保持非零，应重点检查目标应用的记录。

**看到 `snapshot_truncated=1`：**

快照容量确定后又有新节点加入，导致本次输出不完整。请在业务变化较小时重新读取。`node_count` 表示本次实际输出的节点数，连续查询的结果可能不同。

**读取返回内存不足：**

快照内存分配失败时，读取可能返回 `ENOMEM`。驱动会尝试输出 `global_snapshot_error=-ENOMEM`，但该文本可能因读取失败而无法返回。请保留命令错误和内核日志，检查主控端可用内存后重试。

### 2.4 读取开销

驱动在读取时创建临时快照：持有 IPC 锁复制记录，解锁后生成输出。快照在本次内容生成结束后释放，输出缓冲区在文件关闭时释放。该节点没有后台采集任务。

大量节点和较长的白名单可能产生数 MB 输出，建议按需采集，避免高频轮询。读取总耗时包含快照复制和文字生成，IPC 锁仅在复制阶段持有。
