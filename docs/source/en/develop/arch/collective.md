# Collective Communication

AXCCL (the AXCL collective communication library) provides stream-based collective communication
for multi-device and multi-process workloads. Its interface follows NCCL/HCCL conventions, so it
can back a torch_npu-style ProcessGroup. Collective calls are enqueued asynchronously to an
`axclrtStream`; a return does not mean the operation has completed.

This document introduces the AXCCL framework, execution model, and operator coverage.
Per-function parameters, return values, and examples are in the [AXCCL API](../c/axccl_api.md).

Before reading this document, see [System Architecture](system.md), [Core Concepts](concept.md),
and [Programming Model](programming.md) for the Host-Device architecture, the Device / Context /
Stream object model, and the semantics of asynchronous submission and synchronization.

## 1. Objects

| Object | Description | Typical API |
|---|---|---|
| communicator | Binds one logical device to one rank of a collective group; the AXCCL handle | [axCclCommInitRootInfo](../c/axccl_api.md#axCclCommInitRootInfo), [axCclCommFinalize](../c/axccl_api.md#axCclCommFinalize), [axCclCommDestroy](../c/axccl_api.md#axCclCommDestroy) |
| rank / world size | Rank is the index inside the group; world size is the number of members | [axCclCommRank](../c/axccl_api.md#axCclCommRank), [axCclCommCount](../c/axccl_api.md#axCclCommCount) |
| root info | Opaque bootstrap blob generated by rank 0 and broadcast out of band | [axCclGetRootInfo](../c/axccl_api.md#axCclGetRootInfo) |
| Group | Optional batching scope that lets one thread submit the calls of several ranks or several Send/Recv calls together | [axCclGroupStart](../c/axccl_api.md#axCclGroupStart), [axCclGroupEnd](../c/axccl_api.md#axCclGroupEnd) |

World size must be in `[1, 8]`, and rank in `[0, worldSize - 1]`; each rank is used once.
A communicator binds exactly one logical device, so driving several devices from one process
means one communicator per device.
The AXCCL module is reference counted: call [axCclInit](../c/axccl_api.md#axCclInit) after
[axclInit](../c/system_api.md#axclInit), and pair it with [axCclFinalize](../c/axccl_api.md#axCclFinalize)
after all communicators have been finalized and destroyed.

## 2. Bootstrap

Bootstrap goes through root info: rank 0 generates it, the application broadcasts it out of band
(for example over a PyTorch TCPStore or MPI), and every rank then initializes its communicator:

```c
axclInit(NULL);
axCclInit();

/* The communicator borrows the calling thread's current Context on deviceId. */
axclrtSetDevice(deviceId);

axCclRootInfo ri;
if (rank == 0) {
    axCclGetRootInfo(&ri);
}
broadcast(&ri, sizeof(ri));

axCclComm comm;
axCclCommInitRootInfo(&comm, deviceId, &ri, worldSize, rank);
```

- Before [axCclCommInitRootInfo](../c/axccl_api.md#axCclCommInitRootInfo), the calling thread
  must activate `deviceId` and hold a current Context on it. The communicator borrows that
  Context; keep it alive until [axCclCommFinalize](../c/axccl_api.md#axCclCommFinalize) or
  [axCclCommAbort](../c/axccl_api.md#axCclCommAbort) returns.
- The call registers the rank and returns without waiting for the other ranks. Data calls,
  [axCclGroupEnd](../c/axccl_api.md#axCclGroupEnd), and other calls that need the whole group
  wait until every rank has joined. Initialization failures that occur after the call returns
  are reported by [axCclCommGetAsyncError](../c/axccl_api.md#axCclCommGetAsyncError).
- On Linux, AXCCL detects the process layout automatically: the single-process route is used
  when all ranks are in one process, and the multi-process route when each rank is in its own
  process. Other layouts fail.
- [axCclCommInitRank](../c/axccl_api.md#axCclCommInitRank) is an NCCL-style alias of
  [axCclCommInitRootInfo](../c/axccl_api.md#axCclCommInitRootInfo).
- For the single-process multi-device case, [axCclCommInitAll](../c/axccl_api.md#axCclCommInitAll)
  creates one communicator per listed device at once. Activate every listed device with
  [axclrtSetDevice](../c/device_api.md#axclrtSetDevice) first; each communicator uses that device's
  default Context, and the ring is connected before the call returns.

## 3. Execution Model

AXCCL executes on a **ring session**: the communication domain allocates each rank's Device
resources once, and every later operation is one submission on the caller's stream.

| Phase | When | Purpose |
|---|---|---|
| Establish | [axCclCommInitAll](../c/axccl_api.md#axCclCommInitAll), or the first operation of an [axCclCommInitRootInfo](../c/axccl_api.md#axCclCommInitRootInfo) domain | Allocates this rank's Device-side communication buffers and synchronization resources |
| Connect | Immediately after establish | Connects each rank to its successor in the ring once |
| Launch | Every operation | Submits one task on the stream passed by this rank |
| Release | [axCclCommFinalize](../c/axccl_api.md#axCclCommFinalize), or a successful [axCclCommAbort](../c/axccl_api.md#axCclCommAbort) | Frees the domain's Device resources |

The session resources live on the Device and persist between operations. When a bare (ungrouped)
collective call returns depends on the route (for bare Send/Recv, see
[axCclSend](../c/axccl_api.md#axCclSend)):

- Single-process route, after the ring is established: the call enqueues this rank's part and
  returns without waiting for the other ranks to issue the call. Ranks synchronize on the Device.
- Single-process route, before the ring of an
  [axCclCommInitRootInfo](../c/axccl_api.md#axCclCommInitRootInfo) domain is established, and
  always for [axCclAllToAll](../c/axccl_api.md#axCclAllToAll) /
  [axCclAllToAllV](../c/axccl_api.md#axCclAllToAllV): the call only records this rank and returns.
  The call of the last rank enqueues the operation for all ranks.
- Multi-process route: the call returns only after every rank has submitted it.

In every case a successful return does not mean completion. Synchronize the corresponding stream
or event only after every rank's call has returned; that synchronization then blocks until the whole
ring has completed the operation.

Ring order is not the rank order: ranks are ordered by their local chip ID ascending, and the C2C
link from each rank to the next must be online; otherwise ring setup fails. This is a static rule,
not a hardware-discovered physical topology.

## 4. Calling Conventions

**Every rank must issue the same operations in the same order**, with matching operation, data
type, reduction operator, root, and count; this is the standard NCCL/HCCL collective contract.
AXCCL compares the calls of all ranks on both routes and fails a mismatching call. On the
multi-process route, and for bare calls on the single-process route after the ring is established,
a mismatch also fails the domain. Before the ring is established, the pending operation is
discarded for all ranks, including ranks whose calls already returned success.

Each call runs on the calling thread's current Device, which must be the communicator's device.
A NULL `stream` selects the default Stream of the current Context. On the multi-process route, and
for [axCclAllToAll](../c/axccl_api.md#axCclAllToAll) / [axCclAllToAllV](../c/axccl_api.md#axCclAllToAllV)
and [axCclSend](../c/axccl_api.md#axCclSend) / [axCclRecv](../c/axccl_api.md#axCclRecv), the current
Context must be the one captured when the communicator was created. A Device runs CCL work on one
stream at a time: moving a Device's CCL work to another stream fails until its earlier CCL work is
known to be complete, so synchronize the old stream first. On the multi-process route, such a move
fails the domain. Buffers are Device memory from [axclrtMalloc](../c/memory_api.md#axclrtMalloc) on the
communicator's device, and must stay valid until the operation completes on all participating streams.

Synchronization semantics:

- Collective calls such as [axCclAllReduce](../c/axccl_api.md#axCclAllReduce) are accepted as
  described in Section 3, or only collect their arguments inside a group; a return does not mean
  completion. Execution errors are returned when the participating streams are synchronized;
- Only the outermost [axCclGroupEnd](../c/axccl_api.md#axCclGroupEnd) enqueues the group. It waits
  for every rank to finish initialization and validates the whole group first; a validation
  failure discards the whole group, while a failure after part of the group was enqueued fails
  every domain in the group. On the multi-process route, a GroupEnd failure after the processes
  have exchanged the group also fails the domain. A successful return still does not mean completion;
- For a domain that has executed work, the first [axCclCommFinalize](../c/axccl_api.md#axCclCommFinalize)
  synchronizes all participating streams of every rank, then releases the domain's Device
  resources. Keep those streams and Contexts alive until it returns.
  [axCclCommDestroy](../c/axccl_api.md#axCclCommDestroy) then releases the handle; it does not
  finalize the communicator;
- When an operation fails, or its completion is uncertain, the domain becomes failed: later calls
  on it return the failure, and its resources stay allocated. Do not free buffers, destroy
  Contexts, or reset Devices that the domain uses. Any domain failure other than a failure during
  automatic initialization also blocks later launches of every domain in the process for the rest
  of its lifetime; a failure during automatic initialization fails only that domain.
  [axCclCommGetAsyncError](../c/axccl_api.md#axCclCommGetAsyncError) reports it once per
  communicator.

## 5. Operator Coverage

All declared operations are implemented. A single-process communicator supports every feature;
the multi-process route supports a subset:

| API | Current status |
|---|---|
| [axCclAllReduce](../c/axccl_api.md#axCclAllReduce) / [axCclReduce](../c/axccl_api.md#axCclReduce) / [axCclReduceScatter](../c/axccl_api.md#axCclReduceScatter) | Supported on both routes, with `AX_CCL_OP_SUM/PROD/MIN/MAX/AVG` on all declared data types |
| [axCclBroadcast](../c/axccl_api.md#axCclBroadcast) / [axCclAllGather](../c/axccl_api.md#axCclAllGather) / [axCclGather](../c/axccl_api.md#axCclGather) / [axCclScatter](../c/axccl_api.md#axCclScatter) / [axCclBarrier](../c/axccl_api.md#axCclBarrier) | Supported on both routes; data is copied unchanged for all declared data types |
| [axCclAllToAll](../c/axccl_api.md#axCclAllToAll) / [axCclAllToAllV](../c/axccl_api.md#axCclAllToAllV) | Supported on the single-process route only |
| [axCclSend](../c/axccl_api.md#axCclSend) / [axCclRecv](../c/axccl_api.md#axCclRecv) | Supported on both routes; see the API reference for peer matching rules |
| Custom reduction ops ([axCclRedOpCreatePreMulSum](../c/axccl_api.md#axCclRedOpCreatePreMulSum) / [axCclRedOpDestroy](../c/axccl_api.md#axCclRedOpDestroy)) | Supported on the single-process route only, for AllReduce, Reduce, and ReduceScatter |
| Buffer registration ([axCclCommRegister](../c/axccl_api.md#axCclCommRegister) / [axCclCommDeregister](../c/axccl_api.md#axCclCommDeregister)) | Supported on the single-process route only |
| Async error query and abort ([axCclCommGetAsyncError](../c/axccl_api.md#axCclCommGetAsyncError) / [axCclCommAbort](../c/axccl_api.md#axCclCommAbort)) | Supported. Abort succeeds only when all work of the domain is proven complete; on the multi-process route, only before any work was submitted |

`count` is a number of elements. It has no fixed upper limit, because large operations are split
internally; counts smaller than world size and a count of 0 are valid. In-place operation is
selected by passing the same buffer or [AX_CCL_IN_PLACE](../c/reference/macro.md#AX_CCL_IN_PLACE) as
`sendbuff`; partially overlapping buffers are rejected. FP16 has a maximum finite value of 65504, and
an FP16 reduction may exceed it even when every rank's input is finite.

## 6. Deployment Constraints

- The Host library `libaxccl.so`, the Device-side Worker, and `libax_neulink.so` must come from
  the same release; the Host and Device accept only one protocol version, with no fallback;
- Ring collectives require online C2C links between the participating Devices; the ring order
  rule is described in Section 3;
- The multi-process route requires all ranks on the same Host, with the same effective UID and
  network namespace, one rank per process, and distinct physical Devices. See
  [axCclCommInitRootInfo](../c/axccl_api.md#axCclCommInitRootInfo) for the full requirements;
- AXCCL errors use the `AXCL_CCL` sub-module ID `0x5B`;
  [axCclGetErrorString](../c/axccl_api.md#axCclGetErrorString) returns a description of an error code.
