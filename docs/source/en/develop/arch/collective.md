# Collective Communication

AXCCL (the AXCL collective communication library) provides stream-based collective communication
for multi-device and multi-process workloads. Its interface follows NCCL/HCCL conventions, so it
can back a torch_npu-style ProcessGroup. Collective calls are enqueued asynchronously to an
`axclrtStream`; a return does not mean the data path has completed.

This document introduces the AXCCL framework, execution model, and operator coverage.
Per-function parameters, return values, and examples are in the [AXCCL API](../c/axccl_api.md).

Before reading this document, see [System Architecture](system.md), [Core Concepts](concept.md),
and [Programming Model](programming.md) for the Host-Device architecture, the Device / Context /
Stream object model, and the semantics of asynchronous submission and synchronization.

## 1. Objects

| Object | Description | Typical API |
|---|---|---|
| communicator | Binds one logical device to one rank of a collective group; the AXCCL handle | [axCclCommInitRootInfo](../c/axccl_api.md), [axCclCommDestroy](../c/axccl_api.md) |
| rank / world size | Rank is the index inside the group; world size is the number of members | [axCclCommRank](../c/axccl_api.md), [axCclCommCount](../c/axccl_api.md) |
| root info | Bootstrap information generated by rank 0 and broadcast out of band | [axCclGetRootInfo](../c/axccl_api.md) |
| Group | Optional batching entry that submits several ranks' calls from one thread | [axCclGroupStart](../c/axccl_api.md), [axCclGroupEnd](../c/axccl_api.md) |

The current implementation requires a positive world size and accepts `0 <= rank < worldSize`.
A communicator binds exactly one logical device, so driving several devices from one process
means one communicator per device.

## 2. Bootstrap

Bootstrap goes through root info: rank 0 generates it, the application broadcasts it out of band
(for example over a PyTorch TCPStore or MPI), and every rank then initializes its communicator:

```c
axCclRootInfo ri;
if (rank == 0) {
    axCclGetRootInfo(&ri);
}
broadcast(&ri, sizeof(ri));

axCclComm comm;
axCclCommInitRootInfo(&comm, deviceId, &ri, worldSize, rank);
```

`axCclCommInitRootInfo` queries and caches the topology on the Device Context already activated by
the calling thread. It neither creates a discovery-only Worker nor resets the caller's device.
For the single-process multi-device case, `axCclCommInitAll` builds the whole group at once.

## 3. Execution Model

AXCCL executes on a **ring session**: the communication domain allocates each rank's fixed
resources once, and every later collective is just one submission on the caller's stream.

| Phase | When | Purpose |
|---|---|---|
| `ESTABLISH` | `CommInitAll`, or the first operation of an `InitRootInfo` domain | Allocates this rank's stage / scratch double buffers, one signal, and the mcode buffer |
| `CONNECT` | Immediately after `ESTABLISH` | Maps the successor rank's resources once |
| `LAUNCH` | Every collective | Submits one execution on this rank's own stream |
| `REARM` | Domain teardown or reset | Zeroes the signal value and the operation sequence |
| `RELEASE` | Domain teardown | Frees all session resources |

The session resources are **owned by the Device**; the Host only exchanges peer addresses. Ranks
rendezvous on the Device through the signal, so the Host never waits for another rank. `LAUNCH`
uses the `ON_ENQUEUE` boundary of the user stream, so a return only means the operation was
enqueued; the application must still synchronize the corresponding stream or event. Because the
rendezvous is on the Device, that synchronization blocks until the whole ring has completed.

The Host orders the participating ranks by their local chip ID ascending and validates that every
directed C2C peer is online. No adjacency query exists yet, so this is a static rule rather than a
hardware-discovered physical topology.

## 4. Calling Conventions

After the session is established, the Device signal advances one step per `LAUNCH`. **Every rank
must therefore issue the same operations in the same order**; the Host does not validate that the
call sets match, which is the standard NCCL/HCCL collective contract.

Synchronization semantics:

- Collective calls such as `axCclAllReduce` only enqueue; a return does not mean completion;
- `axCclGroupEnd` only reports batch submission / enqueue; the corresponding stream or event still
  has to be synchronized;
- `axCclCommFinalize` only performs the Host state transition and does not replace stream
  synchronization, so the application must synchronize the relevant streams first;
- When an execution's completion is uncertain, the whole session's resources stay pinned and
  further submissions are refused: `REARM` / `RELEASE` return `BUSY`. Isolation and similar
  failures also latch a process-wide failure flag that refuses later launches in that process.

## 5. Operator Coverage

The only implemented operator is `FP32 + SUM` Ring AllReduce, supporting exact in-place aliasing or
non-overlapping out-of-place buffers, with a count from world size up to 1024 elements.

| API | Current status |
|---|---|
| `axCclAllReduce` | Supported (`FP32 + SUM`, ring) |
| `axCclBroadcast` / `axCclReduce` / `axCclAllGather` / `axCclReduceScatter` | Not implemented, returns `AXCL_ERR_CCL_UNSUPPORT` |
| `axCclAllToAll` / `axCclAllToAllV` / `axCclGather` / `axCclScatter` / `axCclBarrier` | Not implemented, returns `AXCL_ERR_CCL_UNSUPPORT` |
| `axCclSend` / `axCclRecv` | Not implemented |
| Custom reduction ops (`axCclRedOpCreatePreMulSum`, ...) | Not implemented |
| Buffer registration (`axCclCommRegister` / `axCclCommDeregister`) | Not implemented |
| Async error query and abort (`axCclCommGetAsyncError` / `axCclCommAbort`) | Not implemented |

The public header also declares the full data-type and reduction-op enums
(`AX_CCL_DT_*`, `AX_CCL_OP_SUM/PROD/MIN/MAX/AVG`). Only `AX_CCL_DT_FP32` with `AX_CCL_OP_SUM`
takes effect today: `axCclAllReduce` rejects any other data type or reduction op with
`AXCL_ERR_CCL_ILLEGAL_PARAM`, while the unimplemented collective entry points return
`AXCL_ERR_CCL_UNSUPPORT`.

## 6. Deployment Constraints

- The Host library, the Device-side Worker, and `libax_neulink.so` must be built and deployed
  together; there is no legacy protocol fallback;
- AXCCL has a single execution wire, protocol version v4, with session opcodes fixed at 15..19.
  1..14 are holes left by the deleted legacy protocol and are never reused;
- `libax_neulink.so` currently registers only the C2C provider and exposes eight entry points:
  `GetTopology` / `ReleaseTopology` and `EstablishRing` / `CheckRingKey` / `ConnectRing` /
  `LaunchRing` / `RearmRing` / `ReleaseRing`;
- The `AXCL_CCL` error sub-module ID is `0x5B`.
